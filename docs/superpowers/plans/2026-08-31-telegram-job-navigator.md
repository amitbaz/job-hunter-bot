# Telegram Job Navigator Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the long Telegram digest with one interactive job card that supports in-place Previous/Next navigation, a job URL button, and a side-effect-free Apply placeholder.

**Architecture:** The scheduled GitHub Actions pipeline still owns discovery/evaluation/PDF delivery. It snapshots the sorted deliverable jobs into a small durable Telegram navigation session stored in Supabase, sends the first card, and marks the jobs message-delivered only after the Telegram send succeeds. A separate Flask webhook runtime receives Telegram callback queries, loads the session from Supabase, edits the same Telegram message, and acknowledges the callback; it never calls Gemini or reads the runner-local SQLite artifact.

**Tech Stack:** Python 3.12, requests, Flask, SQLite for existing job state, Supabase Postgres/Data REST API for navigation sessions, Telegram Bot API, pytest, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-31-telegram-job-navigator-design.md`

## Global Constraints

- Preserve the existing deliverability rule: score must be strictly greater than `60` and decision must be one of the currently deliverable decisions.
- Keep ready-to-apply PDF delivery unchanged.
- Do not implement application submission; `Apply` only answers the callback with `Apply functionality coming soon.`
- Previous/Next edit the same Telegram message; never send a new card per click.
- Navigation does not wrap at either edge.
- Telegram callback data must remain below the Bot API 64-byte limit.
- Use an opaque URL-safe session ID generated with `secrets.token_urlsafe(12)`.
- Navigation sessions expire after 30 days.
- Use the current Supabase `sb_secret_...` backend key in `SUPABASE_SECRET_KEY`; do not introduce a legacy `service_role` key for a new integration.
- The Supabase secret key and Telegram bot token must never appear in source, callback data, logs, URLs, or browser code.
- The webhook must validate `X-Telegram-Bot-Api-Secret-Token` against `TELEGRAM_WEBHOOK_SECRET` using `hmac.compare_digest` before processing updates.
- The webhook runtime must not require Gemini, candidate-profile, or cover-letter secrets.

- [ ] **Step 4: Implement callback encoding/parsing and deterministic sort**

In `src/job_hunter/telegram_navigation.py` implement:

```python
_CALLBACK_ACTIONS = {"n", "a", "x"}


def encode_callback(action: str, session_id: str, index: int) -> str:
    if action not in _CALLBACK_ACTIONS or index < 0:
        raise ValueError("invalid callback payload")
    payload = f"{action}|{session_id}|{index}"
    if len(payload.encode("utf-8")) > 64:
        raise ValueError("callback payload exceeds Telegram limit")
    return payload


def parse_callback(data: str) -> tuple[str, str, int] | None:
    parts = data.split("|")
    if len(parts) != 3 or parts[0] not in _CALLBACK_ACTIONS:
        return None
    try:
        index = int(parts[2])
    except ValueError:
        return None
    if index < 0 or not parts[1]:
        return None
    return parts[0], parts[1], index


def navigation_sort_key(item: DigestItem) -> tuple[int, str, str, int]:
    return (-item.score, (item.company or "").lower(), (item.title or "").lower(), item.job_id)
```

## Implementation Notes for the Executor

- Telegram's `setWebhook` supports `secret_token`, delivered back as `X-Telegram-Bot-Api-Secret-Token`; use it rather than inventing a custom query-string secret.
- Telegram callback queries should always be answered, including no-op actions, so the client-side loading indicator clears.
- `editMessageText` is the intended Bot API method for updating messages that have inline keyboards.
- Current Supabase guidance prefers `sb_secret_...` keys for new server-side integrations; send that key in the `apikey` header, not as `Authorization: Bearer ...`.
- Keep Supabase navigation rows intentionally small: public job-card fields only. Do not store descriptions, CV data, Gemini rationale, or cover-letter material.
- If a future Apply feature needs richer data, use `NavigationCard.job_id` as the stable bridge and design that feature separately; do not expand this navigation snapshot preemptively.

## Definition of Done

The feature is complete only when all automated tests pass and a deployed webhook remains able to navigate an already-sent job card after the GitHub Actions job that created it has exited. The visible Telegram UX must match the approved card layout, the Apply placeholder must have no side effects, and ready-to-apply PDF delivery must remain unchanged.
